<Callout kind="summary" title="이 장의 목적">
앞 장에서 thread 가 *왜 race condition 을 만들고 왜 동기화가 필요한지* 를 봤다면, 이번 장은 **실제로 thread 를 만들고 멈추고 동기화하는 API** 를 다룹니다. POSIX thread(`pthread`) 의 네 묶음 — <b>pthread_create / pthread_join / pthread_mutex_&#42; / pthread_cond_&#42;</b> — 를 시그니처 한 줄까지 뜯어봅니다.
</Callout>


## 1. pthread_create — 새 thread 시작

```c
#include <pthread.h>

int pthread_create(
    pthread_t            *thread,
    const pthread_attr_t *attr,
    void *(*start_routine)(void *),
    void                 *arg
);
```

인자 4 개를 하나씩 짚어 보자.

| 인자 | 역할 |
| --- | --- |
| `pthread_t *thread` | 생성된 thread 를 식별할 **핸들(ID)**. 나중에 join 할 때 이 값을 쓴다. |
| `const pthread_attr_t *attr` | thread 속성 — stack 크기, scheduling policy 등. **보통 `NULL`** (기본값). |
| `void *(*start_routine)(void *)` | thread 가 시작되면 실행할 **함수 포인터**. |
| `void *arg` | 그 함수에 넘겨줄 인자. 어떤 타입이든 포인터로 던질 수 있게 `void *`. |

### `void *(*start_routine)(void *)` 가 뭔 모양?

C 의 함수 포인터 선언은 처음 보면 별표·괄호가 너무 많아 헷갈리는데, **안에서 밖으로 한 겹씩** 벗기면 단순하다.

```c
start_routine                    // 어떤 함수를 가리키는 포인터
*start_routine                   // 그 포인터가 가리키는 "함수 자체"
(*start_routine)(void *)         // 그 함수는 void * 하나를 인자로 받는다
void *(*start_routine)(void *)   // 그 함수는 void * 를 반환한다
```

즉 `start_routine` 은 **"`void *` 하나를 받아 `void *` 를 반환하는 함수"** 를 가리키는 포인터다.

<Callout kind="note" title="왜 `void *` 인가?">
pthread 는 인자와 반환값을 모두 <code>void *</code> 로 다룹니다. <b>어떤 타입이든 포인터로 던질 수 있게</b> 하기 위함이고, 대신 <b>개발자가 직접 적절한 타입으로 cast</b> 해야 합니다. C 에 generic 이 없으니 <code>void *</code> 가 그 역할을 떠맡은 셈이죠.
</Callout>

### 최소 예제

```c
#include <stdio.h>
#include <pthread.h>

typedef struct __myarg_t {
    int a;
    int b;
} myarg_t;

void *mythread(void *arg) {
    myarg_t *m = (myarg_t *) arg;     // void * → myarg_t * 로 캐스팅
    printf("%d %d\n", m->a, m->b);    // "10 20"
    return NULL;                      // 돌려줄 결과 없음
}

int main(int argc, char *argv[]) {
    pthread_t p;                      // 새 thread 의 ID 가 들어올 자리
    myarg_t args = { .a = 10, .b = 20 };

    int ret = pthread_create(&p, NULL, mythread, &args);
    //                       ↑    ↑     ↑         ↑
    //                       핸들 옵션 실행함수    인자
    if (ret != 0) { /* 실패 처리 */ }
    // ... 이 시점에 mythread 가 별도 thread 로 돌고 있다.
}
```

`args` *자체* 가 아니라 **`&args` 의 주소** 를 넘긴다는 점이 핵심이다. `void *` 는 결국 포인터이므로 *값을 전달하려면 주소를 줘야 한다.* 그래서 인자가 여러 개라면 보통 위처럼 **하나의 구조체로 묶어 그 주소를 넘긴다.**


## 2. pthread_join — 끝나길 기다리고 결과 받기

```c
int pthread_join(pthread_t thread, void **value_ptr);
```

- `thread` — 기다릴 대상 thread 의 ID(= `pthread_create` 가 채워 준 그 핸들).
- `value_ptr` — thread 함수가 반환한 `void *` 값을 **받아 올** 자리.

### 왜 `void **` 인가?

함수의 반환값(`void *`)을 *바깥에서 변수에 받아 저장* 하려면, 그 변수의 **주소** 를 알려 줘야 한다. 즉 *"`void *` 값을 바꿔 줄 포인터"* → 한 단계 더 들어간 `void **` 가 된다. 결과가 필요 없으면 그냥 `NULL` 을 넘기면 된다.

```c
pthread_join(p, NULL);   // p 끝날 때까지 기다리되, 결과는 안 받음
```

<PthreadJoinTimeline caption="pthread_create 가 child 를 띄우는 순간 두 thread 가 동시에 진행한다. main 이 pthread_join 에 도달하면 child 가 return 할 때까지 잠들어 있다가, child 의 반환 포인터를 받아 깨어난다." />

### 결과 받아 오기 + ⚠️ Stack 반환의 함정

thread 함수가 두 정수를 돌려주고 싶다고 해 보자.

```c
typedef struct __myret_t {
    int x;
    int y;
} myret_t;

void *mythread(void *arg) {
    myarg_t *m = (myarg_t *) arg;
    printf("%d %d\n", m->a, m->b);

    myret_t *r = malloc(sizeof(myret_t));  // ← heap 에 잡는다 (중요!)
    r->x = 1;
    r->y = 2;
    return (void *) r;
}

int main(...) {
    pthread_t p;
    myret_t  *m;
    myarg_t   args = { 10, 20 };

    pthread_create(&p, NULL, mythread, &args);
    pthread_join(p, (void **) &m);          // m 으로 r 의 주소가 들어온다
    printf("returned %d %d\n", m->x, m->y); // "returned 1 2"
}
```

여기서 **`r` 을 stack 이 아니라 heap (`malloc`) 에 잡는 이유** 가 진짜 중요하다.

<StackReturnDanger caption="local 변수의 주소를 반환하면, 함수 frame 이 사라지는 순간 그 주소는 dangling pointer 가 된다. 다음 함수 호출이 그 자리를 덮어쓰면 호출자는 쓰레기 값을 보거나 crash. thread 함수의 결과는 heap 에 잡아 반환해야 한다." />

```c
int *foo() {
    int x = 10;
    return &x;     // ⚠️ 위험: x 의 stack frame 이 곧 사라진다 → dangling pointer
}
```

함수가 끝나면 그 함수의 stack frame 은 사라진다(주소 자체는 남지만 그 자리에는 곧 다른 호출의 데이터가 쓰여진다). 그 주소를 들고 있으면 **dangling pointer** 가 되어 *언제든 깨지는 코드* 가 된다. 그래서 결과 구조체는 반드시 **`malloc` 으로 heap 에 잡아** 그 포인터를 반환해야 한다.


## 3. Lock — Mutual Exclusion

이제 동기화 차례다. 여러 thread 가 같은 데이터를 동시에 만지면 race condition 이 난다(앞 장에서 본 그대로). 이를 막는 도구가 **lock** 이다. 먼저 용어부터 정리하자.

- **Mutual Exclusion (상호 배제)** — *"여러 thread 가 동시에 들어오면 안 되는 구역에, 한 번에 하나만 들어가게 한다"* 라는 **추상 개념**.
- **Mutex (mutual-exclusion lock)** — 그 상호 배제를 구현하는 **자물쇠 객체**. POSIX 의 `pthread_mutex_t` 가 대표적.
- **Atomic (원자적)** — *"중간에 끼어들 수 없는 하나의 동작처럼"* 실행되는 단위. 보통 한 instruction 수준의 작은 단위에 쓴다.

### Mutex vs Atomic vs Semaphore

셋 다 *"동시에 같이 손대면 안 되는 무언가"* 를 다루지만, **풀고자 하는 모양이 다르다.**

| 도구 | 보호 대상 | 의도 |
| --- | --- | --- |
| **Mutex** | **여러 줄로 된 코드 구역** (critical section) | *"이 구역 전체에 나 혼자 들어갈게."* |
| **Atomic** | **단일 연산** | *"이 연산 하나는 절대 중간에 끊기지 않게 해줘."* |
| **Semaphore** | **동시 진입 인원수** | *"이 자원에는 동시에 N 명까지 들어갈 수 있어."* |

코드로 보면 이렇다.

```c
// Mutex — 구역 전체를 통째로 점유
pthread_mutex_lock(&lock);
counter++;
other_value += counter;
printf("%d\n", counter);
pthread_mutex_unlock(&lock);

// Atomic — 한 줄을 원자적으로
atomic_fetch_add(&counter, 1);
```

Semaphore 는 Mutex 가 *"한 번에 1 명"* 만 들여보낸다면, **카운트가 일반화된 mutex** 라고 보면 된다(예: DB 커넥션 풀이 4 개면 동시에 4 명까지 통과).


## 4. pthread_mutex — 자물쇠 쓰는 법

### 기본 패턴

```c
pthread_mutex_t lock;   // opaque type — 내부 구조는 직접 들여다보지 않는다
                        // (lock 상태 · 잡고 있는 thread ID 등이 들어 있다)

pthread_mutex_lock(&lock);
x = x + 1;              // critical section
pthread_mutex_unlock(&lock);
```

<Callout kind="warning" title="lock 이 막아주는 것은 context switch 가 아니다">
헷갈리기 쉬운 포인트입니다. <b>lock 은 다른 thread 가 같은 critical section 에 들어오지 못하게 막을 뿐</b>, 지금 lock 을 잡고 있는 thread 가 CPU 에서 쫓겨나는 것을 막지는 않습니다. lock 을 든 채로도 timer interrupt 가 와서 context switch 가 일어날 수 있고, 그래도 안전한 이유는 <b>다른 thread 가 그 critical section 에 들어오지 못하기 때문</b>이에요.
</Callout>

### 초기화 — 두 가지 방식

```c
// (1) 정적 초기화 — 선언과 동시에
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

// (2) 동적 초기화 — 런타임에 init 함수로
pthread_mutex_t lock;
int rc = pthread_mutex_init(&lock, NULL);   // 두 번째 인자는 attr (보통 NULL)
assert(rc == 0);                            // 0 이면 성공, 아니면 에러
```

### lock 의 세 가지 변형

```c
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
                            struct timespec *abs_timeout);
```

<LockVariantsComparison caption="lock 은 무한정 기다리고, trylock 은 즉시 포기, timedlock 은 지정 시간까지만 대기한 뒤 실패. 어떤 정책을 쓸지는 '응답성을 보장해야 하나' · '다른 일거리가 있나' 같은 요구사항에 따라 결정한다." />

- **`lock`** — 문 열릴 때까지 **무한정** 기다린다. 일반적인 critical section 보호.
- **`trylock`** — 잠겨 있으면 **즉시** 실패 반환. *"잡을 수 있으면 잡고, 안 되면 다른 일 하자"* 류의 코드에서 유용.
- **`timedlock`** — 지정한 시간까지만 기다린다. **응답성을 보장해야 하는** 코드(예: 일정 시간 안에 반드시 회신해야 하는 RPC 핸들러)에서 무한 대기를 막을 때.


## 5. Condition Variable — 조건이 만족될 때까지 자다 깨다

mutex 만으로는 못 푸는 문제가 있다. *"A 가 어떤 작업을 끝낼 때까지 B 가 기다린다"* 같은 시나리오에서, B 가 mutex 만 잡고 상태를 계속 다시 확인하면 **CPU 를 낭비하는 spin (= busy-wait)** 이 된다. 그래서 *"조건이 만족될 때까지 자고 있다가 누가 깨워 주면 다시 본다"* 라는 메커니즘이 필요한데, 이게 **condition variable** 이다.

```c
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
// 현재 thread 를 잠재운다. 깨어날 때 자동으로 mutex 를 다시 잡아 준다.

int pthread_cond_signal(pthread_cond_t *cond);
// cond 에서 기다리는 thread 중 (적어도) 하나를 깨운다.
```

### 정석 패턴 — "초기화될 때까지 기다리기"

부모 thread 가 자식이 어떤 초기화를 끝내고 알려 줄 때까지 기다리는 전형적 코드다.

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  init = PTHREAD_COND_INITIALIZER;
int             initialized = 0;

// === Thread A: 기다리는 쪽 ===
pthread_mutex_lock(&lock);
while (initialized == 0)              // ← if 가 아니라 while
    pthread_cond_wait(&init, &lock);
pthread_mutex_unlock(&lock);

// === Thread B: 깨우는 쪽 ===
pthread_mutex_lock(&lock);
initialized = 1;
pthread_cond_signal(&init);
pthread_mutex_unlock(&lock);
```

이 짧은 코드 안에 **놓치면 안 되는 5 가지 약속** 이 동시에 들어가 있다. 한 장으로 묶어 보자.

<CondVarProtocol caption="A 는 lock 후 조건을 확인하고, 거짓이면 cond_wait — 이 함수는 mutex 를 풀고 잠드는 동작을 atomic 하게 수행한다. B 가 lock 을 잡고 상태를 바꾼 뒤 signal 을 쏘면 A 가 깨어나는데, 이때 cond_wait 안에서 mutex 를 다시 잡아 주고 나서야 반환한다. 깨어난 A 는 while 로 한 번 더 검사한 뒤 빠져나간다." />

읽어야 할 포인트:

1. **`cond_wait` 는 "mutex 풀기 + 잠들기" 가 atomic 이다.** 따로 했다간 *"풀고 → 자기 직전에 B 가 signal → 영원히 못 깨어남"* 의 lost wakeup 이 생긴다.
2. **`cond_signal` 도 lock 안에서 친다.** 그래야 *"상태 변경 → 알림"* 이 한 덩어리로 보인다.
3. **깨어난 thread 는 자동으로 mutex 를 다시 잡고 나온다.** 그러니 wait 호출은 *마치 풀린 적 없는 것처럼* 그 뒤 코드에서 mutex 보호가 그대로 이어진다.
4. **`while` 로 다시 검사.** (아래에서 자세히)
5. **`init` 과 `initialized` 는 다른 변수.** `init` 은 condition variable(잠/깨우기 채널), `initialized` 는 실제 상태를 담는 일반 변수.

### Q1. 왜 `if` 가 아니라 `while` 인가?

`pthread_cond_wait` 에서 깨어났다고 해서 *조건이 반드시 만족된 상태라는 보장이 없다.* 이유는 두 가지.

- **Spurious wakeup** — 시스템 사정으로 신호 없이도 깨어나는 경우가 명세상 허용된다.
- **다른 thread 가 먼저 끼어들었을 수 있다.** signal 받고 깨어났는데, 내가 mutex 를 다시 잡기 전에 또 다른 waiter 가 먼저 잡고 상태를 만져 버리면, 내가 깨어났을 때는 이미 조건이 거짓일 수 있다.

그래서 **깨어난 뒤 한 번 더 검사** 해야 안전하다 — `if` 가 아니라 `while`. 이것은 *방어적 코드* 가 아니라 **API 가 그렇게 쓰도록 만들어졌다.**

### Q2. `signal` 이 왜 필요? mutex 만 풀면 자동으로 안 깨어나나?

`pthread_cond_wait` 에 들어간 thread 는 **blocked 상태로 잠들어 있다.** spin 으로 폴링하지 않으니까 *누가 명시적으로 깨워야* 다시 살아난다. 그 *"명시적으로 깨우는"* 신호가 `pthread_cond_signal` 이다. mutex 의 unlock 만으로는 잠든 thread 가 깨어나지 않는다.

<Callout kind="tip" title="cond variable 과 state variable 의 역할 분리">
<b>condition variable (<code>init</code>)</b> — 잠/깨우기의 동기화 채널. 값을 비교하거나 읽지 않는다.<br/>
<b>state variable (<code>initialized</code>)</b> — 실제 상태를 담는 보통 변수. <code>while</code> 의 조건 검사는 <b>이쪽</b>으로 한다.<br/>
두 변수는 <b>반드시 같은 mutex 로 보호</b>되어야 합니다. 그래야 상태 변경과 signal 이 한 덩어리로 보입니다.
</Callout>


## 6. 컴파일

pthread 를 쓰는 코드는 링크 단계에 thread 라이브러리를 붙여 줘야 한다.

```bash
gcc -o main main.c -Wall -pthread
```

- `-Wall` — 가능한 경고는 다 켜기.
- `-pthread` — 컴파일·링크 모두에 pthread 설정을 추가. 단순 `-lpthread` 보다 **이쪽이 권장**된다(`_REENTRANT` 같은 매크로도 함께 정의해 주기 때문).


## 한 줄 요약

<Callout kind="summary" title="Thread API 4 종 한눈에">
• <b>pthread_create</b> — 새 thread 시작. 4 번째 인자(<code>void *</code>) 로 데이터 전달.<br/>
• <b>pthread_join</b> — thread 종료 대기 + 반환값 수신. ⚠️ 반환은 반드시 <b>heap</b> 으로(<code>&local</code> 금지).<br/>
• <b>pthread_mutex_&#42;</b> — critical section 의 상호 배제. <code>lock</code> / <code>trylock</code> / <code>timedlock</code> 으로 대기 정책 선택.<br/>
• <b>pthread_cond_&#42;</b> — 조건이 만족될 때까지 잠들었다 깨기. 반드시 <code>while</code> 로 재검사, 항상 mutex 안에서.
</Callout>
